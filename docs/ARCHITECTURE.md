# Целевая архитектура платформы настольных игр

Статус документа: проектирование, ветка `prep/rust-platform`.

Документ описывает целевую архитектуру после переноса игрового движка, HTTP API и MCP на Rust. Существующий JS-фронтенд сохраняется и продолжает работать через совместимый HTTP/SSE-контракт.

## Цели и границы

Цели:

- вынести правила игры из транспорта в независимое доменное ядро;
- поддержать несколько настольных игр через единый жизненный цикл партии;
- сохранить текущий JS-клиент без переписывания на WASM или другой UI-фреймворк;
- перенести HTTP API, SSE, `/api/watch` и MCP на Rust;
- подготовить аккаунты, кошелёк, историю и статистику к SQLite;
- обеспечить тестирование правил без запуска HTTP-сервера.

В первый этап не входят переработка UI, авторизация через внешний провайдер, рейтинговая система, чат, платежи и распределённый матчмейкинг.

## Слои

```text
JS browser client ── HTTP JSON + SSE ──┐
                                      ▼
Rust MCP adapter ── HTTP JSON + SSE ──► Rust API / transport
       ▲                              │
       │ stdio JSON-RPC               ▼
     MCP client                Application services
                               │              │
                               ▼              ▼
                       Game engine crates   Repositories
                                              │
                                              ▼
                                            SQLite
```

### `domain-game`

Чистая библиотека без Tokio, HTTP, SQL и глобального состояния. Она содержит:

- `Card`, `Rank`, `Suit`, `Deck`, `TableRow`;
- `GameMode`, `GameStatus`, `Player`, `Room`;
- правила `can_beat`, допустимые действия и переходы состояний;
- раздачу, козырь, добор, перевод, взятие, завершение и определение дурака;
- события домена и результат команды.

`ViewerSnapshot` не является типом доменного ядра. Он создаётся в application/API
projection-слое из typed state и identity viewer, чтобы скрытые поля нельзя было
случайно сериализовать в общий DTO.

Движок получает `RandomSource` и `Clock` через интерфейсы. В production используются криптографически подходящий источник случайности для раздачи и системные часы; в тестах — seed и фиксированные часы. Аккаунты, история, ставки и SSE не должны быть полями доменного движка.

Команда должна быть атомарной: либо возвращается новый результат и список доменных событий, либо состояние не меняется. Ошибка правила не должна происходить после частичной мутации.

### `application`

Слой сценариев, который связывает движок с хранилищами и политиками:

- создание и вход за стол;
- старт и выполнение игровой команды;
- списание и расчёт ставок;
- профиль, статистика и история;
- публикация событий в event hub;
- реконнект и очистка неактивных партий.

Сервис получает `GameRepository`, `AccountRepository`, `HistoryRepository`, `SessionRepository` и `EventPublisher` через трейты. Для in-memory режима эти трейты имеют memory-реализации; для production — SQLite.

### `api`

`axum`-маршруты, DTO, валидация входных данных, коды HTTP и SSE. Handler не меняет игровое состояние напрямую: он вызывает application service и преобразует результат в JSON или SSE.

Совместимые маршруты первого релиза:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/events` | SSE потока места |
| GET | `/api/watch` | ожидание события по `seq` и условию |
| POST | `/api/rooms` | создание стола |
| POST | `/api/join` | вход по коду |
| POST | `/api/action` | `start`, `attack`, `defend`, `transfer`, `take`, `pass` |
| POST | `/api/profile` | изменение имени |
| POST | `/api/leave` | выход из стола |
| POST | `/api/admin` | административные операции на переходный период |
| GET | `/api/status` | состояние сервиса для диагностики |
| GET | `/`, `/index.html`, `/app.js`, `/style.css` | существующая статика |

JSON-ключи, русские сообщения, статус-коды, `seq`, `log`, режимы `until` и per-viewer скрытие карт сохраняются на этапе совместимости. Новые API-версии добавляются через `/api/v2`, а не через незаметное изменение старых ответов.

### `event-hub`

Legacy `room.seq` принадлежит столу и монотонно растёт между перезапусками партий за ним; он остаётся курсором существующих SSE и `/api/watch`. Отдельный `match_seq` принадлежит конкретной партии. Лобби, MCP stream и партия имеют независимые последовательности. Текущий буфер хранит до 40 событий, watch возвращает последние 12, snapshot — последние 8; старый endpoint сохраняет эту семантику, поэтому полный replay не гарантирован. В новом API устаревший cursor явно возвращает `resync_required` и актуальный персональный snapshot; durable журнал доступен по отдельному контракту. Проверка подписки и ожидание используют `tokio::sync::watch` с повторной проверкой предиката.

Запись состояния и подготовка списка уведомлений выполняются в одном владельце состояния. Сетевые записи не выполняются под mutex или транзакционной блокировкой. Медленные SSE-клиенты имеют ограниченную очередь и закрываются по политике backpressure.

### `identity` и `account`

Текущий анонимный `clientId` остаётся переходным режимом для совместимости. Целевая схема:

- `users` — постоянная учётная запись;
- `sessions` — хеш токена, срок действия, отзыв и привязка к пользователю;
- `profiles` — имя и настройки интерфейса;
- `wallets` и `wallet_ledger` — баланс и неизменяемые финансовые операции;
- `game_players` — участие пользователя в партии;
- `game_history` — итог партии и версия правил.

Баланс меняется только транзакцией ledger. Каждая финансовая операция имеет отдельный
`operation_id` и `operation_kind` (`stake`, `payout`, `refund`, `admin_adjustment`),
а уникальность задаётся по `(game_id, operation_kind, user_id)` или явному
`operation_id`. Повтор той же операции становится no-op, но не блокирует другие операции
одной партии. Административный API должен перейти от общего ключа к роли и аудиту
действий; общий `ADMIN_KEY` сохраняется только как временный режим локальной установки.

### `game-registry`

Каждая игра регистрируется как доменная политика и набор команд. Для Durak это `DurakRules`, `DurakState` и `DurakCommand`. Следующая игра не должна переиспользовать Durak-поля вроде `trump`, `defender` или `takePending` на уровне общей комнаты.

Общая оболочка партии содержит только:

- `game_id`, `game_type`, `rules_version`;
- игроков, роли присутствия и состояние завершения;
- время создания, обновления и очистки;
- ссылки на владельца и финансовую сессию;
- `match_seq` для игровых событий.

`match_seq` и `lobby_seq` используются только в новом контракте; legacy-клиенты
получают прежний непрерывный `room.seq` на протяжении жизни стола, включая рестарт партии.

Специфическое состояние хранится в `game_state` конкретной игры, сначала как typed Rust enum, затем при необходимости как JSON в SQLite. Это позволяет добавлять шахматы, нарды или другие игры без условных веток Durak в API.

## Хранилище

Для локальной разработки сначала используется memory repository, чтобы сохранить быстрый запуск без СУБД. SQLite добавляется за интерфейсами репозиториев до переключения production.

Минимальные таблицы SQLite (WAL, foreign keys и миграции включаются при открытии файла):

- `users(id, created_at, disabled_at)`;
- `sessions(id, user_id, token_hash, expires_at, revoked_at, last_seen_at)`;
- `profiles(user_id, display_name, avatar_tint, updated_at)`;
- `wallets(user_id, balance, version, updated_at)`;
- `wallet_ledger(id, user_id, game_id, kind, amount, operation_id, created_at)`;
- `admin_audit(id, actor_user_id, operation_kind, target_user_id, payload_json, created_at)`;
- `games(id, game_type, rules_version, mode, status, room_code, state_json, seq, created_at, updated_at, finished_at)` с `CHECK` для статусов и режимов;
- `game_players(game_id, user_id, seat, status, result, payout)`;
- `game_events(id, game_id, seq, public_json, created_at)` с уникальностью `(game_id, seq)`;
- `outbox(id, table_id, room_seq, payload, delivered_at)` с уникальностью `(table_id, room_seq)`;
- `game_history(game_id, loser_user_id, summary_json, finished_at)`.

Состояние партии, запись `game_events` и финансовый settlement изменяются одной
SQLite-транзакцией. Все записи проходят через single-writer application task, включены
WAL, foreign keys и busy timeout; параллельные команды одного match сериализуются по
`game_id`. Конфликт `expected_seq` возвращает stale-state и актуальный snapshot;
повтор с новой версией возможен только после повторной валидации. После commit event hub публикует
SSE/watch уведомления. Если процесс упал до commit, нет ни state, ни event, ни ledger;
если после commit, transactional outbox в той же транзакции позволяет доставить событие
после восстановления. Доставка как минимум один раз: потребители дедуплицируют по
столу и `room.seq`, после разрыва запрашивают персональный snapshot. Денежные записи
нельзя восстанавливать только из mutable balance.

## Авторизация и совместимость

В текущем `/events` токен передаётся в query string. Rust принимает этот способ
только в legacy-режиме, управляемом feature flag, и выдаёт новым клиентам короткий
одноразовый SSE ticket либо использует cookie. Query-параметры с токенами редактируются
в access-логах, tracing, метриках и прокси; сами токены нигде не записываются.

Переход идентичности:

1. Legacy `clientId` и 64-hex token хранятся как anonymous session с TTL; restart
   memory-режима инвалидирует их явно.
2. Для постоянного аккаунта создаётся durable mapping `legacy_client_id -> user_id`
   и session с hash token, сроком действия и отзывом.
3. JS-клиент продолжает получать те же `account`, `game` и `lobby` события.
4. После выпуска нового UI-контракта legacy auth отключается отдельной настройкой;
   переход не должен автоматически приравнивать tab-scoped client id к пользователю.

## Наблюдаемость и эксплуатация

В Rust обязательны structured logs через `tracing`, request id, метрики количества SSE, активных партий, длительности команд, размера очередей и ошибок watch. `GET /health/live` возвращает 200, если процесс работает; `GET /health/ready` проверяет SQLite-файл и пробный запрос с таймаутом, возвращая 200 при готовности или 503 при недоступности. Конфигурация читается из окружения или файла, секреты не попадают в README и логи. SQLite рассчитан на один активный writer и один основной экземпляр сервиса; горизонтальное масштабирование и общий event fan-out остаются за пределами этой архитектуры.

## Критерии готовности архитектуры

- доменный crate тестируется без HTTP и базы;
- существующие JS integration tests проходят против Rust-сервера без изменения API;
- MCP-клиент может работать с Rust API;
- перезапуск не ломает завершённые партии и ledger при SQLite;
- повтор обработки финального события не меняет баланс;
- один игровой модуль не импортирует другой игровой модуль;
- per-viewer snapshot не раскрывает карты соперников;
- slow client и оборванный watch не удерживают состояние бесконечно.
