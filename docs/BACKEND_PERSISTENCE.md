# Хранение данных и аутентификация Rust backend

Rust-сервер открывает `DURAK_DB` (по умолчанию `data/durak.sqlite`) и применяет SQL-миграции при запуске. Каталог миграций определяется относительно пути манифеста серверного crate во время сборки и должен быть доступен при запуске.

Rust API принимает сессии клубных аккаунтов и подтверждённых аккаунтов Discord. Браузерная форма входа использует имя и пароль клубного аккаунта. Старые гостевые записи сохраняются в базе. `npm start` запускает Rust-сервер. Node-сервер используется для сравнения и тестирования и принимает гостевые сессии.

## Настройка Discord OAuth

Для сборки учётные данные Discord не нужны. Для нового входа задайте вместе `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` и `DISCORD_REDIRECT_URI` и зарегистрируйте точный redirect URI в портале разработчиков Discord. Требуется HTTPS; HTTP допускается только для loopback. При частичной настройке сервер не запускается. Без настройки Discord доступен вход по имени и паролю клубного аккаунта. `GET /api/auth/providers` объявляет `discord` только при наличии конфигурации и SQLite.

При запуске OAuth клиент отправляет `POST /api/auth/discord/start`, сохраняет возвращённый `flowSecret` в `sessionStorage` вкладки и переходит по URL авторизации Discord. Сервер создаёт одноразовый state и PKCE verifier на пять минут в памяти. Страница возврата отправляет `code`, `state` и `flowSecret` в `POST /api/auth/discord/complete`. Браузерный клиент очищает параметры OAuth через `history.replaceState`, сохраняет выданную сессию в `sessionStorage` и подключается к SSE/gameplay API. Сервер обменивает код, получает подтверждённую идентичность Discord и возвращает `{clientId, token}`. Ответы с секретами имеют `Cache-Control: no-store`; токен нужно защищать и использовать HTTPS. Перезапуск отменяет ожидающие входы. Новый вход меняет токен сессии и отключает прежний SSE-поток. Токены доступа Discord не сохраняются.

Токен приложения хранится в `sessionStorage`, а не в HttpOnly cookie; выход в личном кабинете очищает данные вкладки, но не отзывает серверную сессию. Обмен OAuth с реальными учётными данными Discord ещё нужно проверить до развёртывания. `POST /api/auth/discord/start` ограничен 10 попытками на IP за пять минут, 4096 отслеживаемыми IP и 4096 ожидающими входами. Эти ограничения действуют в одном процессе и требуют дополнения на обратном прокси.

## Миграция активных комнат

При восстановлении сохранённой комнаты со статусом идущей партии сервер проверяет каждого игрока, который её не покинул: у `discord:`-аккаунта проверяется привязка, у `temp:`-аккаунта проверяется наличие сохранённого хеша пароля. Если хотя бы один игрок не проходит проверку, запуск прерывается с ошибкой, содержащей идентификаторы комнаты и игрока. Сервер не отменяет такую партию автоматически и не возвращает ставки; гостевые данные не привязываются автоматически.

Администратор должен внимательно разрешить миграцию игроков или отмену затронутой комнаты до повторного запуска, с учётом банка, ставок и балансов. Сначала сохраните резервную копию базы и проверьте последствия выбранного решения; не удаляйте комнату или записи игроков без сверки расчётов. Готовая автоматическая процедура отмены или возврата ставок для этого случая здесь не предусмотрена.

## Хранение

SQLite хранит привязки идентификаторов, хеши токенов и паролей, сопоставления Discord-аккаунтов, снимки аккаунтов и игровых переходов, а также историю лобби. `commit_transition` атомарно сохраняет снимок комнаты с номером последовательности и изменения аккаунтов с проверкой версии; идентичный повтор идемпотентен. При запуске `AppState::with_repository` проверяет снимки, загружает активные комнаты и аккаунты и отклоняет противоречивые данные. SSE-подключения, активные сессии и ожидающие OAuth-запросы хранятся в памяти процесса. Клиенты могут переоткрыть SSE с сохранёнными учётными данными после перезапуска. Обычный переход, который завершает партию, сохраняет историю лобби в той же транзакции.
