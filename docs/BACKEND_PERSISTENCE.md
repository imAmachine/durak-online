# Хранение данных и аутентификация Rust backend

Rust-сервер открывает `DURAK_DB` (по умолчанию `data/durak.sqlite`) и применяет SQL-миграции при запуске. Каталог миграций определяется относительно пути манифеста серверного crate во время сборки и должен быть доступен при запуске.

Для доступа к Rust API требуется подтверждённый аккаунт Discord. Старые гостевые записи сохраняются в базе, но вход по ним недоступен; автоматической привязки к Discord нет. Node backend запускается отдельно командой `node server.js` только для сравнения и тестирования. Он допускает гостевые аккаунты, не поддерживает обязательный вход через Discord и несовместим с текущим браузерным входом. `npm start` запускает Rust-сервер.

## Настройка Discord OAuth

Для сборки учётные данные Discord не нужны. Для нового входа задайте вместе `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` и `DISCORD_REDIRECT_URI` и зарегистрируйте точный redirect URI в портале разработчиков Discord. Требуется HTTPS; HTTP допускается только для loopback. При частичной настройке сервер не запускается. Без настройки Discord новый вход и доступ к приложению для не вошедших пользователей недоступны. `GET /api/auth/providers` объявляет `discord` только при наличии конфигурации и SQLite.

Клиент отправляет `POST /api/auth/discord/start`, сохраняет возвращённый `flowSecret` в `sessionStorage` вкладки и переходит по URL авторизации Discord. Сервер создаёт одноразовый state и PKCE verifier на пять минут в памяти. Страница возврата отправляет `code`, `state` и `flowSecret` в `POST /api/auth/discord/complete`. Браузерный клиент очищает параметры OAuth через `history.replaceState`, сохраняет выданную сессию в `sessionStorage` и подключается к SSE/gameplay API. Сервер обменивает код, получает подтверждённую идентичность Discord и возвращает `{clientId, token}`. Ответы с секретами имеют `Cache-Control: no-store`; токен нужно защищать и использовать HTTPS. Перезапуск отменяет ожидающие входы. Новый вход меняет токен сессии и отключает прежний SSE-поток. Токены доступа Discord не сохраняются.

Токен приложения хранится в `sessionStorage`, а не в HttpOnly cookie; полноценного интерфейса выхода и отзыва нет. Обмен OAuth с реальными учётными данными Discord ещё нужно проверить до развёртывания. `POST /api/auth/discord/start` ограничен 10 попытками на IP за пять минут, 4096 отслеживаемыми IP и 4096 ожидающими входами. Эти ограничения действуют в одном процессе и требуют дополнения на обратном прокси.

## Миграция активных комнат

При восстановлении сохранённой комнаты со статусом идущей партии сервер проверяет каждого игрока, который её не покинул: идентификатор должен начинаться с `discord:` и иметь запись привязки Discord в базе. Если хотя бы один игрок не проходит проверку, запуск прерывается с ошибкой, содержащей идентификаторы комнаты и игрока. Сервер не отменяет такую партию автоматически и не возвращает ставки; гостевые данные не привязываются автоматически.

Администратор должен внимательно разрешить миграцию игроков или отмену затронутой комнаты до повторного запуска, с учётом банка, ставок и балансов. Сначала сохраните резервную копию базы и проверьте последствия выбранного решения; не удаляйте комнату или записи игроков без сверки расчётов. Готовая автоматическая процедура отмены или возврата ставок для этого случая здесь не предусмотрена.

## Хранение

SQLite хранит старые привязки идентификаторов, сопоставления подтверждённых Discord-аккаунтов, снимки аккаунтов и игровых переходов. `commit_transition` атомарно сохраняет снимок комнаты с номером последовательности и изменения аккаунтов с проверкой версии; идентичный повтор идемпотентен. При запуске `AppState::with_repository` проверяет снимки, загружает активные комнаты и аккаунты и отклоняет противоречивые данные. SSE-клиенты, токены сессий и ожидающие OAuth-flow остаются в памяти процесса. Интеграция истории находится в работе; её состояние необходимо проверить. Дополнительная проверка совместимости и готовности к эксплуатации остаётся необходимой.
