# Раздельное развёртывание

Пример ниже сохраняет один публичный HTTPS origin: nginx отдаёт разрешённые HTML, JS и CSS файлы frontend и передаёт `/api/*`, `/events`, `/readyz` одному Rust backend. Node и npm на production-хосте не нужны. Существующий `npm start` и встроенная раздача остаются доступными для разработки. Отдельный API origin и CORS эта конфигурация не поддерживает.

## Подготовка

1. На сборочной машине с Rust соберите `cargo build --manifest-path rust/Cargo.toml --release --locked -p platform-server -p platform-mcp`. Проверьте совместимость целевой системы и библиотек. Скопируйте бинарники `platform-server` и, если нужен MCP, `platform-mcp` из `rust/target/release/` на соответствующие машины.
2. Скопируйте в `/srv/durak/web` только `index.html`, `admin.html`, `css/style.css` и нужные файлы с расширением `.js` из корневого каталога `js/` и `.css` из корневого каталога `css/`; для итоговых HTML обязательны `/js/main.js` и `/js/admin-main.js`. Каталог должен быть доступен nginx только на чтение. Не публикуйте корень репозитория, базу или секреты. Пример [nginx.conf](nginx.conf) ограничивает статику точечными HTML URL и файлами `/js/*.js` и `/css/*.css`, включая `/admin`, и явно задаёт MIME. Обновляйте HTML, JS и CSS согласованной версией.
3. Передайте backend отдельный каталог миграций через `DURAK_MIGRATIONS_DIR`; путь по умолчанию сохраняет поведение разработки. Для встроенной раздачи можно задать `DURAK_STATIC_DIR`, но в схеме с nginx он не нужен. SQL-файлы должны быть доступны backend на чтение, а frontend и миграции должны обновляться согласованными версиями.

## Запуск backend и прокси

Запустите backend под отдельной непривилегированной учётной записью, в приватной сети, например:

```sh
HOST=127.0.0.1 PORT=4173 DURAK_DB=/var/lib/durak/durak.sqlite /usr/local/bin/platform-server
```

Каталог базы должен быть доступен на запись только этой учётной записи. Для панели задайте длинный случайный `ADMIN_KEY` через защищённое окружение службы; без ключа панель отключена. Не включайте ключ в командную строку, журнал или репозиторий. Если Discord нужен, задайте вместе `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI`; зарегистрируйте точный HTTPS redirect URI того же публичного origin в Discord. Иначе оставьте все три переменные незаданными. Секреты храните отдельно от статики и ограничьте доступ к ним.

Включите пример конфигурации в контекст `http` nginx, замените имя сервера, пути сертификата и ключа, путь статики и адрес backend. Выполните `nginx -t` и перезагрузите nginx только после успешной проверки. Пример слушает только HTTPS; настройте действительный сертификат и его обновление. При отдельном TLS-прокси перед nginx дополнительно защитите внутренний канал и настройте таймауты всех промежуточных прокси. Публичный доступ к порту backend закройте сетевыми правилами.

`/events` передаётся без буферизации: backend отправляет keepalive каждые 15 секунд. `/api/watch` ожидает до 60 секунд, таймаут чтения прокси равен 75 секундам. Межсетевые устройства должны допускать такие соединения. Ссылки приглашений используют origin страницы; пути и query-параметры сохраняются. Не включайте кэширование ответов API и SSE. В примере выключен access log, поскольку query SSE/watch содержит токены, а URL также могут содержать коды приглашений или OAuth; настройте и остальные журналы и мониторинг так, чтобы они не записывали секреты.

Backend определяет адрес для ограничения Discord OAuth по TCP peer, а не по заголовкам прокси. За одним nginx все пользователи разделяют лимит OAuth (10 попыток за 5 минут); forwarded-заголовки это не исправят. Учтите этот лимит до публичного запуска. Пример не добавляет внешнего ограничения частоты запросов. Не доверяйте клиентским заголовкам с IP без отдельного проектирования доверенной цепочки прокси.

## Данные, обновление и проверка

Используется SQLite в режиме WAL; храните базу на постоянном локальном томе. Для резервирования работающей базы используйте SQLite Online Backup API или `sqlite3 /var/lib/durak/durak.sqlite '.backup /secure/path/durak-backup.sqlite'`, а не копирование одного основного файла во время работы. Защитите копии и проверяйте восстановление на отдельной базе. Перед обновлением сделайте резервную копию, остановите единственный backend, установите согласованные бинарник и миграции, запустите его и проверьте `/readyz`; затем обновите статику и прокси. Обратный переход со схемой новой версии заранее не гарантирован — при необходимости восстанавливайте совместимую резервную копию. Не запускайте несколько backend на одной базе: комнаты и события также хранятся в памяти процесса.

Проверьте через публичный HTTPS `/`, `/admin`, `/css/style.css`, `/js/main.js`, `/js/admin-main.js`, `/readyz`, `/api/status`, ответы 404 для файлов с другими расширениями и неразрешённых путей, заголовок `Cache-Control: no-store` у всей статики и сохранение `/?code=...`. На тестовых аккаунтах проверьте вход, создание и вход по приглашению, непрерывное получение событий и переподключение SSE, ожидание watch до 60 секунд, панель и восстановление после перезапуска. При настроенном Discord отдельно проверьте настоящий OAuth callback. Не выводите токены в журналы при проверке.

Rust MCP — отдельный stdio-процесс, запускаемый MCP-клиентом, например `/usr/local/bin/platform-mcp` с `DURAK_URL` на приватный backend или публичный HTTPS origin. Он принимает готовые сессии или учётные данные клубного аккаунта; подробности в [README MCP](../rust/crates/platform-mcp/README.md). Защищайте переменные, файл сохранённых сессий и транспорт. Полная проверка совместимости и production-сценариев остаётся отдельной задачей.
